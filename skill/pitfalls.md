## 1. Verilog 位宽截断：`(x - 1'd0)` 会把整个减法压成 1 位（★ 血泪教训）

- **触发条件**：写移位量或常量偏移时用了「非理想的窄常量」参与运算，例如
  `rounded = prod + (64'sd1 <<< (cfg_shift - 1'd0));`
- **现象**：绝大多数输入都 bit-exact 对得上，只有**极少数点差 1**（本项目 312 个输出里错 1 个：
  dut=0x1b golden=0x1a）。极易被误判为"舍入误差可以接受"而放过
- **根因**：Verilog 表达式的位宽由**参与运算的最宽操作数**决定，但**常数是自定宽的**：
  `1'd0` 是 1 位宽 → 整个 `cfg_shift - 1'd0` 被按 1 位运算 → 结果几乎恒为 0 或 1
  → 舍入常数从 `1<<(shift-1)` 变成 `1<<0`，负半轴上的结果就偏了
- **排查步骤**（这是最有价值的部分）：
  1. 先确认「模拟量是否一致」：在 Python 里独立算出该点的 `acc`，与 RTL 探针对上 → 排除 MAC 翻车
  2. 把该点的 `prod / rounded / shifted` 三级中间量**分别打印**，与 Python 逐级比对
     → 本项目一步锁定：`prod` 对、`rounded` 偏差恰好 = `1<<16`（即应为 `1<<(shift-1)`）
  3. 把可疑表达式抄进一个 10 行的独立 tb 单独验证（本项目的 `dbg_s1.v`，5 分钟定位）
- **解决**：把常数写成与上下文一致的宽度，或直接用裸数字：
  ```verilog
  wire signed [63:0] rounded = prod + (64'sd1 <<< (cfg_shift - 8'd1));  // 正确
  // 或
  wire signed [63:0] rounded = prod + (64'sd1 <<< (cfg_shift - 1));     // 裸 1 自动升宽
  ```
- **从哪些失败中总结**：2026-10-14 `pw_conv_engine` 首轮 5 种子中 2 组各错 1 个点。
  根因定位耗时约 25 分钟。
- **推广（与题目无关）**：**凡是用移位实现定点量化、寻址、对齐的地方都要自查**。
  这是一条「98% 通过率比 0% 通过率更危险」的典型陷阱——
  如果只跑一组随机种子，很可能直接漏掉。
  **务必跑多组随机种子回归**，这正是它们存在的意义。

## 2. xsim 中 BRAM 数组写口必须用阻塞赋值激励，且不能与同数组的读在同一 always 块

- **触发条件**：testbench 用 `<=` 非阻塞赋值驱动一个被 DUT 用于数组写入的端口信号
- **现象**：`bram_wt[0]` 读出 `xx`（未初始化），而 `bram_wt[1]`、`[7]`、`[8]` 全部正常；
  写入探针显示 DUT 采样到的 `we/addr/data` 完全正确 → 信号对、存储没写进去
- **根因**：两个叠加因素：
  ① TB 用 `@(posedge clk); wt_we <= 1;` 时，DUT 的 `always @(posedge clk)` 在同一时刻
     采样到的是**旧值**（非阻塞更新在同一时隙的 NBA 区域才生效），第一笔写入被丢掉；
  ② DUT 内部把"数组写口"和"数组读口"放在同一个 always 块里，xsim 对该情形的处理
     与综合工具不一致，容易只保留读路径
- **排查步骤**：
  1. 先确认是"信号问题"还是"存储问题"：在 TB 里直接 `$display` 该数组元素
  2. 加写口采样探针（打 `we/addr/data`），若采样值正确 → 问题在存储侧
  3. 若某几个地址写进去了、另一个没进去，且那个地址恰好是第一个 → 时序竞争
- **解决**：
  ① TB 里改为 `@(negedge clk)` 建立激励、`@(posedge clk)` 等待，让 DUT 在时钟沿前
     就能看到稳定值；
  ② RTL 里把写口拆成独立的 `always` 块，与读口彻底隔离：
  ```verilog
  always @(posedge clk) if (wt_we) bram_wt[wt_waddr] <= wt_wdata;   // 写：独立块
  always @(posedge clk) w_d <= bram_wt[rd_waddr];                    // 读：独立块
  ```
- **从哪些失败中总结**：2026-10-14 首次跑通 `pw_conv_engine` 仿真时，
  32 个输出通道中只有第 0 个通道全错（25 个像素值全 `xx`），其余 11 个通道全对。
  定位耗时约 20 分钟，靠"打探针 + 二分缩小"完成。
- **推广**：任何"AXI 寄存器配置 + BRAM 写入"的控制通路都要注意这条，
  与题目、板卡无关。

## 2. Git Bash 的 unzip 通配符提取会产出空目录

- **触发条件**：Windows + Git Bash 环境下 `unzip archive.zip "dir/pattern/*" -d out`
- **现象**：命令退出码 0、无报错，但目标目录为空
- **根因**：该版本 unzip 的通配符展开与 Windows 路径处理不兼容
- **解决**：用完整路径逐个提取，或改用 Python：
  ```python
  import zipfile
  z = zipfile.ZipFile('a.zip')
  for i in z.infolist():
      if i.filename.split('/')[1] in wanted:
          z.extract(i, 'out')
  ```
- **从哪些失败中总结**：2026-10-14 从 ALINX `course_s1.zip` 提取例程时踩到。
- **推广**：跨平台脚本一律不依赖 shell 通配符，用 Python 或显式路径。

## 3. Git Bash 调用 Vivado 的 .bat 包装器时 `=` 会被吞掉

- **触发条件**：`xsim.bat tb -R --testplusarg CIN=8`
- **现象**：`Expected a switch but found 8`，xsim 打印帮助后退出
- **根因**：Git Bash 传递含 `=` 的参数给 cmd 包装脚本时被拆分
- **解决**：**不要用命令行参数传配置**，改为写文件让 testbench `$readmemh` 读取
  （本项目用 `sim/data/params.hex`）。这一改动同时提升了可复现性：
  同一份 params.hex + 同一份数据 = 同一结果
- **从哪些失败中总结**：2026-10-14 配置 `pw_conv_engine` 仿真参数时踩到。
- **推广**：仿真/构建脚本的配置一律走文件，不走命令行（跨平台且可存档）。
