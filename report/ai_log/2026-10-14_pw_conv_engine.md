## 2. 纠错轨迹 A：BRAM 第 0 号元素读出 x（定位 ~20 分钟）

| 阶段 | 内容 |
|---|---|
| 现象 | 32 个输出通道中，只有第 0 个通道 25 个像素全为 `xx`，其余 11 通道全对 |
| AI 最初判断 | 以为是 FSM 的地址初值问题，建议改状态机 |
| 人类介入 | 要求在 TB 里直接打印 `dut.bram_wt[0..8]`，看是写入问题还是读出问题 |
| 定位过程 | ① 打印数组：`[0]=xx` 但 `[1][7][8]` 都对 → 存储侧问题<br>② 加写口采样探针：`addr=0 data=d0 we=1` **完全正确** → 信号没问题<br>③ 推断为「TB 用非阻塞赋值 + DUT 同沿采样」的时序竞争，且写口与读口同在一个 `always` 块 |
| 修复 | ① RTL 里写口拆成独立 `always` 块；② TB 改为 `@(negedge clk)` 建立激励 |
| 沉淀 | 写入 `skill/pitfalls.md` 第 2 条 |

**教训**：AI 第一反应是改设计逻辑（成本高、风险大）。**应先加"观测点"再改代码**——
打印存储内容、打印端口采样值，两步就把"设计错"和"激励错"分开。

## 3. 纠错轨迹 B：极少数点差 1（★ 最有价值的记录）

| 阶段 | 内容 |
|---|---|
| 现象 | 单跑一组种子全 PASS；跑 6 组回归时，seed=1 和 seed=7 各错 1 个点（312 里错 1，差 1） |
| AI 最初判断 | **判断错误**——认为是"定点量化的舍入误差，属正常范围，可放宽容差" |
| 人类介入 | 要求"查清这 1 个点到底是舍入误差还是逻辑 bug" |
| 定位过程 | ① 用 Python 独立重算该点中间量：`acc=-13` 与 RTL 探针一致 → MAC 阶段排错<br>② 逐级打印 `prod / rounded / shifted`，与 Python 对比：<br>　`prod` 一致（-12942969）<br>　`rounded` 差 65536，恰好 = `1<<16`，**而正确值应为 `1<<(shift-1)` = `1<<16`**<br>③ 怀疑 RTL 表达式：`(cfg_shift - 1'd0)`<br>④ 抄进 10 行独立 tb 验证：`rounded` 确实少加 65536 → 确认 |
| 根因 | `1'd0` 是 1 位常量 → 整个 `cfg_shift - 1'd0` 按 1 位运算 → 移位量退化为 0 或 1 → 舍入常数算错 |
| 修复 | `(cfg_shift - 8'd1)`，或直接用裸常数 `1` |
| 沉淀 | `skill/pitfalls.md` 第 1 条（列为 ★ 级） |

**教训（本项目最重要的一条方法论）**：
> **「98% 通过率比 0% 通过率更危险。」**
> 如果只跑一组随机种子，这个 bug 会一路带到上板阶段，最终表现为
> "硬件和 PyTorch 总差一点，怎么调量化都调不回来"，届时排查成本是现在的十倍。
> **多随机种子回归不是可选项，而是必须项。**
>
> 另：AI 给出"这是正常舍入误差"时不能直接接受——**定点实现里没有"差不多"，
> 只有 bit-exact 和错**。量化误差属于"模型层面"（影响 Top-1 掉点），
> 而这里同一套公式在同一硬件上算出两个不同结果，属于"实现层面"的确定性错误。

## 4. AI 协作的经验提炼（→ 待写入 `skill/prompt_workflow.md`）

1. **让 AI 写 RTL 时必须同时要求写"黄金参考"**——否则无法验收
2. **配置参数走文件、不走命令行**：既规避 Git Bash 传 `=` 的坑，又保证可复现
3. **让 AI 先给"观测方案"再给"修改方案"**：观测成本远低于改动成本
4. **对 AI 的"容差论"保持警惕**：在确定性数字电路里，位宽/移位/符号扩展类
   bug 都表现为"偶发差 1~2"，与真正的数值容差极难区分，必须逐级对中间量
